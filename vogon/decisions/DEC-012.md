# DEC-012 — Expected results are fixed in the requirement before the implementation exists

**Context.** A test catches an error because the expected result was derived
independently of the code. A test whose expected value was read off a run of
the code cannot fail, whatever it asserts. This is bad test design and it is
not new, but an agent falls into it readily: the code is in front of it,
running it is cheaper than working the value out, and a failing test reads as
work not yet finished.

The damage is specific to a validated system. Elsewhere a user eventually
complains. Here the suite is green, the coverage is full, the matrix is
complete, the package is signed, and nothing ever compared the system to the
requirement.

**Options.**

Require the tests to be written before the implementation. This puts the
ordering on the test code, which is where it is easiest to subvert: a test
written first and adjusted until it passes is indistinguishable afterwards
from one written last.

Require the expected values to be fixed in the requirement, by a person,
before either the code or the tests exist.

**Decision.** The acceptance block of a requirement carries concrete expected
results, written from the requirement rather than from any run, and a named
person accepts it before the record leaves `proposed`. The test specification
is written from the accepted blocks and approved before the code. Tests
implement it. Whether a test file is written before or after the
implementation is left to the developer, because the value it asserts was
fixed before either existed.

**Consequences.** No test may cite a requirement whose acceptance block has
not been accepted, so a risk-bearing requirement cannot be verified until a
person has said what correct means for it. That is friction, and it is the
point. What is not enforceable is whether the person wrote the criteria or
approved what an agent proposed; the record names who is answerable and stops
there. The drafting instructions tell the agent to derive expected values from
the requirement and never from a run, and nothing checks that.

**Example.** A requirement says a dose is rounded to two decimals. The
acceptance block, accepted by a named person, says an input of 1.235 gives
1.24. The implementation truncates and returns 1.23. The test asserts 1.24
because that is what the accepted block says, and it fails on the first run.
