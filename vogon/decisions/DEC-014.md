# DEC-014 — A plan is written before the code, retired when spent, and the documentation outlives it

**Context.** Between a requirement and the code there is a plan: what will be
built, in what order, against which records. The agent needs one, the reviewer
wants to see it before the code arrives, and it stops being true as soon as
the code exists.

**Options.**

Leave the plan to the agent with no instruction and no place to put it. The
plan then lives in a conversation, a reviewer never sees it before the code,
and nothing connects it to the records it implements.

Ship a skill for it, give it a place in the host project, and retire it when
it is spent.

**Decision.** VOGON ships the instructions for writing a plan. A plan states
what is going to be built, names the records it implements, and is written
before the code. It lives at `vogon/plans/plan_<slug>.md` in the host project.
When it has been implemented or abandoned it is moved to `vogon/plans/done/`,
which is never read again and never updated. Anything that has to stay true
goes into the documentation before the plan is retired, and the documentation
is derived from the code as it stands.

**Consequences.** A reviewer sees the intent before the diff. Nothing
committed may depend on a plan, because a spent plan is not maintained and
saying otherwise would make the retired copies part of the specification. The
documentation, not the plan, is what a later reader trusts, and it is derived
from the code rather than from what was intended.

**Example.** A plan naming three requirements is written, reviewed and
implemented. The design specification is regenerated from the code, and the
plan moves to `vogon/plans/done/`. A question six months later is answered from
the documentation, not from the retired plan.
