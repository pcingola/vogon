# DEC-002 — Records sit in a visible vogon directory, tool state in .vogon

**Context.** The records need a home in the host project that does not collide
with the host project's own documentation and can be given its own review rules.

**Options.**

Everything under `.vogon/`. One directory for the tool to own, at the cost of
hiding the records: a dot-directory is skipped by `ls`, excluded by many
tooling globs, collapsed in code review, and never browsed.

Inside the host project's existing `docs/`. No new top-level directory, at the cost
of mixing controlled records with prose and losing a clean boundary for
`CODEOWNERS`.

A visible `vogon/` for records, `.vogon/` for tool state.

**Decision.** Records, held sources and generated output go in `vogon/`.
`.vogon/` holds tool state only — cached tracker state, the trace collector's
output — and is gitignored. Configuration goes in `vogon.yaml` at the host
project root, in the format the records already use.

**Consequences.** The records are visible to anyone browsing the repository and
`vogon/` can carry its own `CODEOWNERS` entry and review rules. Configuration
sits outside the host project's build file, so a host project in any language can be
configured and no second parser is needed. `vogon/out/` is generated and will be
overwritten, so it needs the same warning `docs/` carries in this repository.

**Example.** Someone clones the VOGON project and reads `vogon/requirements/TRK/` without
installing VOGON. Deleting `.vogon/` costs nothing but a re-read of the
tracker.
