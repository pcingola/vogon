# DEC-011 — External systems are named by role, and the product is configuration

**Context.** VOGON reaches systems it does not own: the tracker, the test
manager, the repository host, the document system. Which product fills each
role is decided by the company's IT and quality organisation, and a regulated
company usually mandates both the product and the access path to it. A
company that runs Jira may forbid the vendor's MCP server and require its own.

**Options.**

Name the products throughout, in records, documentation and generated text.
Precise while the assumption holds, and wrong in every project that made a
different choice, with the correction spread across every file that named
them.

Name the role, and treat the product and its access path as configuration.

**Decision.** Records, documentation and generated text name the role. What
VOGON states for each role is the operations it needs: for the tracker, read
an issue and its approval state, create an issue, link two issues; for the
test manager, create or find a test issue, link it to a requirement issue,
read its review state, import a result keyed to a build. The product, and the
MCP server through which it is reached, are configuration supplied by the
project. Where nothing fills a role, VOGON ships a default that configuration
can replace.

**Consequences.** DEC-004 continues to hold: version 0.1 is written and tested
against one set of products and abstracts over nothing in code. This decision
governs vocabulary and configuration, not layering, so adding a second product
is still a refactor. An install check is needed, because a configured server
that does not provide a required operation has to fail at install rather than
at first use.

**Example.** A company runs Jira behind an MCP server it wrote itself and forbids
the vendor's. The project configures that server as its tracker and VOGON
works against it unchanged, because no record and no generated document names
Jira.
