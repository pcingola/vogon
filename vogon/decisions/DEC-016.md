# DEC-016 — An identifier is a type, an optional module, and a number

**Context.** Records are referred to by id in prose, in commit messages, in
test markers and in tracker fields. The id has to be recognisable on sight
where none of the file is in front of the reader, unambiguous in a host project with
several modules, and usable in a host project with none.

**Options.**

A number alone, with the type in the frontmatter. The shortest form, and
unreadable everywhere the frontmatter is not present: a commit message naming
`12` says nothing.

A type and a number, with the module carried only in the frontmatter. Uniform,
and it puts every module on one number sequence, so nothing groups and two
people minting an id at the same time collide more often.

A type, a mandatory module, and a number. Groups well, and forces a host project
with one module to invent a name for it and repeat it in every id.

A type, an optional module, and a number.

**Decision.** An id is `<TYPE>-<NUMBER>` or `<TYPE>-<MODULE>-<NUMBER>`. The
type is three or more uppercase letters and names one of the four record types.
The module is one or more uppercase letters and digits, is chosen by the host
project, is not restricted by VOGON beyond its shape, and is omitted by a
host project that does not use modules. The number is one or more digits, minted per
type and module, and compared numerically.

**Consequences.** An id carries its own meaning in a commit message or a test
marker. A host project can adopt modules later without renumbering, at the cost of
old ids reading differently from new ones. VOGON cannot validate a module name,
only its shape, so a typo in one mints a new sequence rather than failing, and
what catches it is the check for a reference to a record that does not exist.

**Example.** A host project with no modules mints `REQ-1`. A host project split into
`TRK` and `REC` mints `REQ-TRK-1` and `REQ-REC-1`, which are two records and
both are requirement number one.
