# DEC-024 — Expected results are fixed in the requirement, and the order of approvals is reported rather than required

**Context.** `DEC-012` fixed the expected results in the requirement before
the implementation exists, and also required the test specification to be
approved before the code was written. A test catches an error because its
expected result was derived independently of the code, and an agent reads an
expected value off a run of the code readily, because the code is in front of
it and a failing test reads as unfinished work. That part of `DEC-012` stands.

The ordering part does not hold in practice. A host project installs VOGON part way
through, a Test Lead is appointed after the code exists, or a procedure puts
the approvals in a different order. VOGON cannot prevent any of these, because
the approvals are given by people in systems VOGON does not control
(`CON-001`), and a rule nobody can meet is ignored along with the rules next
to it. What an auditor finds is an approval dated after the thing it governs
was used (`FACT-004`), and that is visible in the dates.

**Options.**

Keep `DEC-012` as written. A host project that ran a step late has no way to
comply, and the late approval is still given, without being reported.

Drop the ordering and say nothing about it. The findings `FACT-004` describes
then reach the auditor before they reach the host project.

Keep the expected-value rule, and report every approval given after what it
governs was used.

**Decision.** The acceptance block of a requirement carries concrete expected
results, written from the requirement and never from a run of the code, and a
named person accepts it before the record leaves `proposed`. A test may name
only a requirement whose acceptance block has been accepted (`REQ-TRC-8`).
Tests implement the accepted block, and a failing test is made to pass by
changing the code, never the expected value. Whether a test is written before
or after the implementation is left to the developer, because the value it
asserts was fixed before either.

The pipeline is followed where the host project allows. A step that was skipped is
done afterwards, with its real dates, and VOGON reports every approval given
after what it governs was used (`REQ-TRK-11`). The report is a finding for the
host project to answer, and does not make the late approval valid or invalid.
This replaces `DEC-012`.

**Consequences.** A risk-bearing requirement still cannot be verified until a
person has said what correct means for it. A host project that approves its test
cases after their results were imported can finish the pipeline, and the late
approval appears in the report with both dates, where the host project sees it
before an auditor does. What is not enforceable is whether the person wrote the
criteria or approved what an agent proposed; the record names who is
answerable and stops there.

**Example.** A requirement says a dose is rounded to two decimals. The
acceptance block, accepted by a named person, says an input of 1.235 gives
1.24. The implementation truncates and returns 1.23, and the test asserts 1.24
and fails on the first run. The Test Lead approves the test issue two days
after the first result was imported against it, and the next run reports the
test issue, the approval date and the import date.
