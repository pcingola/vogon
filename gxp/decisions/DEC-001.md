# DEC-001 — Records are markdown files in the project's git repository

**Context.** The specification has to be editable by developers in the same
change as the code, reviewable in a pull request, and readable by someone who
does not have the tool installed.

**Options.**

A database or a dedicated requirements tool. Queryable and able to enforce
structure, at the cost of a second place to look, a second set of credentials,
and a specification that cannot be changed in the same commit as the code.

The tracker alone, with no repository copy. One place to look, and every edit
costs a web form. Text under approval becomes expensive to change, which is
what makes teams back-fill requirements at the end.

Markdown with YAML frontmatter in the repository, pushed to the tracker.

**Decision.** Markdown with YAML frontmatter, one file per record, in the
project's git repository. The frontmatter is the queryable structure and the
body is the prose. No database.

**Consequences.** Diffs, branches, review and history come from git at no cost.
Structure is enforced by a checker rather than by a schema the store imposes,
so an invalid record can exist until the checker runs. Querying across records
means reading files, which is acceptable at the scale a single project reaches
and would not be at the scale of an organisation.
