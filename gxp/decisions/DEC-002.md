# DEC-002 — Records sit in a visible gxp directory, tool state in .vogon

**Context.** The records need a home in the host project that does not collide
with the project's own documentation and can be given its own review rules.

**Options.**

Everything under `.vogon/`. One directory for the tool to own, at the cost of
hiding the records: a dot-directory is skipped by `ls`, excluded by many
tooling globs, collapsed in code review, and never browsed.

Inside the project's existing `docs/`. No new top-level directory, at the cost
of mixing controlled records with prose and losing a clean boundary for
`CODEOWNERS`.

A visible `gxp/` for records, `.vogon/` for tool state.

**Decision.** Records, held sources and generated output go in `gxp/`.
`.vogon/` holds tool state only — cached tracker state, the trace collector's
output — and is gitignored. Configuration goes in `[tool.vogon]` in
`pyproject.toml` rather than in a file of its own.

**Consequences.** The records are visible to anyone browsing the repository and
`gxp/` can carry its own `CODEOWNERS` entry and review rules. A project that
does not use Python needs somewhere else for configuration, which version 0.1
does not have to solve. `gxp/out/` is generated and will be overwritten, so it
needs the same warning `docs/` carries in this repository.

**Example.** Someone clones the project and reads `gxp/requirements/TRK/` without
installing VOGON. Deleting `.vogon/` costs nothing but a re-read of the
tracker.
