§ 1.0 Why VOGON

The problem is well understood.

Modern GxP software development requires rigorous traceability between requirements, risks, implementation, verification, and change control.

Unfortunately, it also requires developers.

Developers produce working software, which is helpful, and then decline to produce the documentation proving that they produced it, which is a finding. VOGON resolves this tension by generating the documentation regardless of developer cooperation, enthusiasm, or continued employment.

“Turn your development velocity into regulatory evidence.”

§ 2.0 Platform

Derived, then enforced.

VOGON sits between the tools engineers use and the quality system auditors read. It derives the regulated record from what actually happened in the repository and the pipeline, then renders the parts a regulator asks for.

A ticket becomes a requirement with an identifier. The requirement gets a risk score. A pull request claims the requirement, and VOGON checks the claim against the diff, the tests that ran, and the reviews that happened. Complete links pass the gate. Incomplete links fail it, with the missing artefact named.

A passing review looks the same, minus the stamp, plus a link to the updated traceability matrix. Deficiencies are reported individually, so that each may be remediated, documented, and re-submitted individually.

Correct the named deficiency. Attach the evidence. Re-request review. The gate re-evaluates against the same criteria, plus any criteria introduced since your last submission.

Median time from first submission to merge is eleven days. The code change is typically finished on day one.

§ 5.0 Support

Reporting an issue.

VOGON does not accept GitHub Issues. Defects and feature requests are submitted on paper, in triplicate, under procedure VGN-PROC-001.

  1. Print Form VGN-ISS-001 — Preliminary Notice of Intent to Report an Issue in triplicate.
  2. Complete all three copies by hand, in blue or black ink. Typed submissions are rejected.
  3. Obtain five signatures: requestor, requestor’s manager, Quality Assurance, system owner, independent witness.
  4. Submit each copy separately — original by registered mail, quality copy by fax, controlled copy retained in a fire-resistant cabinet for fifteen years.
  5. Allow 30–45 business days for acknowledgement. Acknowledgement does not constitute acceptance.

Issues opened directly through GitHub are closed with: REJECTED — Electronic submission received without corresponding paper record. For urgent production incidents, follow the same process and write URGENT in the upper-right corner of all three copies. Processing times are unaffected.
