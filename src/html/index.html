§ 1.0 Platform

One linked record of the software lifecycle.

VOGON sits between the tools engineers use and the quality system auditors read. It derives the regulated record from what actually happened in the repository and the pipeline, then renders the parts a regulator asks for.

STAGE 01

Requirements

User requirements and functional specifications, uniquely identified, versioned, and kept in step with the backlog as it changes.

Source — Jira epics, stories, product docs
STAGE 02

Risk assessment

GAMP 5 categorisation and functional risk assessment with severity, probability and detectability scored, and mitigations linked to real controls.

Source — Requirements, system context, change history
STAGE 03

Implementation evidence

Which commits, pull requests and reviews implemented which requirement — with reviewer identity and timestamps captured as they occur.

Source — GitHub, GitLab
STAGE 04

Verification

IQ/OQ/PQ protocols, test-case-to-requirement mapping, and executed results with logs and artefacts attached as objective evidence.

Source — CI/CD runs, manual test records
STAGE 05

Traceability

A bidirectional requirement ↔ risk ↔ code ↔ test ↔ evidence matrix. Gaps are flagged the day they appear, not the week before an inspection.

Source — The linked record itself
STAGE 06

Change control

Change records with impact assessment, regression scope, approval routing and post-implementation review, generated from pull request metadata.

Source — PR metadata, risk model
STAGE 07

Validation package

Validation plan, traceability matrix, test summary, deviation log and validation summary report — assembled, indexed and exported on demand.

Output — PDF/A, Word, CSV, signed JSON manifest
STAGE 08

Deviation handling

Deviations open a CAPA automatically, with root cause, corrective action, effectiveness check and closure evidence tracked to completion.

§ 2.0 How it works

A ticket becomes a requirement. A requirement becomes evidence.

A ticket becomes a requirement with an identifier. The requirement gets a risk score. A pull request claims the requirement, and VOGON checks the claim against the diff, the tests that ran, and the reviews that happened. Complete links pass the gate. Incomplete links fail it, with the missing artefact named.

§ 3.0 The gate

Every pull request is reviewed against the requirement it claims.

VOGON evaluates the change against the risk class of the code it touches and the evidence available at that commit. A passing review looks the same, minus the stamp, plus a link to the updated traceability matrix.

vogon-bot commented on #482
VOGON has reviewed PR #482.

  ✗  Requirement traceability incomplete
  ✗  Risk assessment requires update
  ✓  Verification evidence attached
  ✗  Change justification uses the phrase "small fix"

        ┌─────────────────┐
        │    REJECTED     │
        │      VOGON      │
        └─────────────────┘

Please correct the deficiencies and resubmit.

This rejection has generated CAPA-1847.

What the gate actually checks

  • 01Requirement link. The PR names a requirement, and the diff plausibly implements it.
  • 02Risk currency. The risk assessment postdates the last functional change to the affected component.
  • 03Verification. Tests covering the requirement ran, on this commit, and passed.
  • 04Review integrity. An approving reviewer who is not the author, recorded with identity and timestamp.
  • 05Justification. A stated reason for the change. “Small fix” is not a stated reason.

Both outcomes are recorded. The rejection is also a record. Everything is a record.

A gate failure, as experienced by the requestor Figure 3 — Human factors study · VGN-HF-002 · Rev 1

Deficiencies are reported individually so that each may be remediated, documented, and re-submitted individually.

Remediation loop Per VGN-PROC-002

Correct the named deficiency. Attach the evidence. Re-request review. The gate re-evaluates against the same criteria, plus any criteria introduced since your last submission.

Median time from first submission to merge is eleven days. The code change is typically finished on day one.

§ 4.0 Why VOGON

The problem is well understood.

Modern GxP software development requires rigorous traceability between requirements, risks, implementation, verification, and change control.

Unfortunately, it also requires developers.

Developers produce working software, which is helpful, and then decline to produce the documentation proving that they produced it, which is a finding. VOGON resolves this tension by generating the documentation regardless of developer cooperation, enthusiasm, or continued employment.

§ 10.0 Support

Reporting an issue.

VOGON does not accept GitHub Issues. Defects and feature requests are submitted on paper, in triplicate, under procedure VGN-PROC-001.

  1. Print Form VGN-ISS-001 — Preliminary Notice of Intent to Report an Issue in triplicate.
  2. Complete all three copies by hand, in blue or black ink. Typed submissions are rejected.
  3. Obtain five signatures: requestor, requestor’s manager, Quality Assurance, system owner, independent witness.
  4. Submit each copy separately — original by registered mail, quality copy by fax, controlled copy retained in a fire-resistant cabinet for fifteen years.
  5. Allow 30–45 business days for acknowledgement. Acknowledgement does not constitute acceptance.

Issues opened directly through GitHub are closed with: REJECTED — Electronic submission received without corresponding paper record. For urgent production incidents, follow the same process and write URGENT in the upper-right corner of all three copies. Processing times are unaffected.
